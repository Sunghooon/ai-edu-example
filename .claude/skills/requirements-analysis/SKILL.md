# 요구사항 분석 스킬

이 스킬은 ISO 26262(기능안전), A-SPICE 4.1(SYS.1 이해관계자 요구사항 도출, SYS.2 시스템 요구사항 분석, SWE.1 소프트웨어 요구사항 분석), ISO/IEC 25010(품질특성)을 준수하는 요구사항 산출물을 작성하기 위한 절차와 규칙을 정의한다.

## 적용 범위 (다른 스킬과의 경계)

- 이 스킬은 요구사항의 **도출·명세·검증기준 정의**까지만 다룬다. 실제 테스트 케이스(입력값/절차/기대결과)는 만들지 않는다 — 시스템 수준은 `sw-system-test`, 통합 수준은 `software-integration-testing`, 유닛 수준은 `tdd`가 담당한다.
- 아키텍처/상세설계(컴포넌트, 인터페이스, 내부 알고리즘)는 다루지 않는다 — `architecture-design`, `detailed-design`을 사용한다.
- 비기능요구사항의 품질특성 분류에 사용하는 **ISO/IEC 25010**(ISO 25000 SQuaRE 시리즈의 제품 품질모델)은 `sw-system-test`가 비기능 테스트 케이스를 묶을 때 쓰는 품질특성 체계와 동일하다. 두 스킬이 서로 다른 분류 체계를 만들지 않고 이 8개 특성을 공통으로 사용한다.

## 0. 템플릿 우선순위 (필수 선행 절차)

요구사항을 작성하기 전에 반드시 다음 순서로 템플릿을 확인한다.

1. 사용자가 이번 대화에서 직접 제시한 템플릿이 있으면 그것을 그대로 따른다.
2. 저장소의 표준 산출물 템플릿(`WP_Templates/`)을 사용한다. 세부 위치·형식별 처리 방법·라이선스 주의사항은 `references/templates.md`를 반드시 먼저 읽고 따른다. 핵심 템플릿:
   - SW 요구사항 명세서: `WP_Templates/Engineering/SoftwareRequirementsAnalysis/TPL-SWE1-001_SW 요구사항 명세서 템플릿.docx`
   - Use Case 명세서: `WP_Templates/Engineering/SoftwareRequirementsAnalysis/TPL-SWE1-002_Use Case 명세서 템플릿.docx`
   - Use Case 다이어그램: `WP_Templates/Engineering/SoftwareRequirementsAnalysis/TPL-SWE1-003_Use Case 다이어그램 템플릿.drawio`
   - 양방향 추적 매트릭스: `WP_Templates/Engineering/Traceability/TPL-TRC-001_양방향 요구사항 추적 매트릭스 템플릿.xlsx`
   - 전체 템플릿 목록과 적용 산출물 매핑은 `WP_Templates/PRC-TPL-001_표준 산출물 양식 등록부.xlsx`를 따른다.
3. 위 템플릿 파일을 저장소에서 찾을 수 없는 경우에만 아래 "3. 기본 요구사항 템플릿(Default)"을 사용하되, 결과물 상단에 "표준 템플릿을 찾지 못해 기본 템플릿을 사용함"이라고 명시한다.

사용자가 이번 대화에서 별도 템플릿을 제시하면 그 즉시 우선순위 1번으로 전환하고, 기존에 다른 템플릿으로 작성된 산출물은 새 템플릿에 맞게 갱신이 필요함을 사용자에게 알린다.

## 1. 준수 표준 요약

- **A-SPICE 4.1 SYS.1/SYS.2/SWE.1**: 요구사항의 명세, 구조화, 상호작용/충돌 분석, 검증기준 정의, 이해관계자와의 합의, 양방향 추적성 확보, 일관성 유지가 Base Practice로 요구된다.
- **ISO 26262**: 안전 관련 요구사항은 위험원인분석(HARA)에서 도출된 안전목표(Safety Goal)로부터 기능안전요구사항(FSR) → 기술안전요구사항(TSR) → 시스템/SW/HW 안전요구사항으로 이어지는 추적 사슬을 가져야 하며, 각 요구사항에 ASIL(QM, A, B, C, D)이 명시되어야 한다. 안전 무관 요구사항은 QM으로 표기한다.
- **ISO/IEC 25010**: 비기능요구사항은 품질특성(기능적합성, 성능효율성, 호환성, 사용성, 신뢰성, 보안성, 유지보수성, 이식성) 중 하나 이상에 매핑되어야 한다.

## 2. 요구사항 작성 절차

1. **입력 확인**: 이해관계자 요구/상위 산출물(있다면)을 확인한다. 없으면 사용자에게 요청한다.
2. **분류**: 각 요구를 기능/비기능/안전/제약사항으로 분류한다.
3. **작성(명확성 확보)**: "4. 명확성 규칙(EARS)"에 따라 단일 의미·단일 문장으로 서술한다.
4. **기능요구사항 다이어그램화**: "5. 기능요구사항과 UML/SysML" 규칙에 따라 필요한 다이어그램을 함께 제시한다.
5. **비기능요구사항 품질특성·검증방안**: "6. 비기능요구사항과 ISO/IEC 25010" 규칙에 따라 특성 매핑과 실행 가능한 검증방법을 함께 제시한다.
6. **안전요구사항 처리**: 안전 관련이면 "7. ISO 26262 처리" 규칙을 적용한다.
7. **추적성 확보**: "8. 추적성 확보 방안"의 ID 체계와 추적성 매트릭스를 실제로 생성/갱신한다(제안만 하고 끝내지 않는다).
8. **일관성 검사**: "9. 일관성 확보 방안"의 체크리스트를 이번에 작성한 요구사항 전체에 대해 실제로 수행하고 결과를 보고한다.
9. **결과 보고**: 작성한 산출물 목록, 사용한 템플릿(프로젝트 템플릿/기본 템플릿), 추적성 매트릭스 갱신 내역, 일관성 검사 결과를 요약한다.

## 3. 기본 요구사항 템플릿 (Default)

프로젝트 템플릿이 없을 때 사용하는 개별 요구사항 서식이다.

```
### [REQ-ID] 요구사항 제목

- **유형**: 기능 / 비기능 / 안전 / 제약
- **출처**: (상위 요구사항 ID, 이해관계자 요구 등)
- **서술(EARS)**: <EARS 패턴을 따른 요구사항 문장>
- **근거(Rationale)**: <왜 필요한지>
- **ISO 26262 ASIL**: QM / A / B / C / D
- **ISO/IEC 25010 품질특성** (비기능요구사항인 경우): <특성/부특성>
- **관련 다이어그램** (기능요구사항인 경우): <다이어그램 종류 및 링크>
- **검증기준/방법**: <Test/Analysis/Inspection/Demonstration 중 실행 가능한 방법 + 구체적 절차>
- **추적성**:
  - Trace-From(상위): <ID>
  - Trace-To(하위: 설계/코드/테스트, 확정 전이면 "미정"): <ID 또는 미정>
- **상태**: Draft / Reviewed / Approved
- **개정이력**: <버전, 일자, 변경내용>
```

## 4. 명확성 규칙 (EARS)

모든 요구사항 서술은 EARS(Easy Approach to Requirements Syntax) 패턴 중 하나를 따른다.

- 유비쿼터스: "<시스템>은 <응답>을 수행해야 한다."
- 이벤트 기반: "<트리거>일 때, <시스템>은 <응답>을 수행해야 한다."
- 상태 기반: "<상태>인 동안, <시스템>은 <응답>을 수행해야 한다."
- 원치 않는 동작: "<조건>이면, <시스템>은 <응답>을 수행해야 한다."
- 선택적 기능: "<기능 포함 조건>에서, <시스템>은 <응답>을 수행해야 한다."

추가로 다음을 지킨다.

- 한 요구사항에는 하나의 요구만 담는다("~하고, ~해야 한다"처럼 접속사로 여러 요구를 묶지 않는다).
- "적절히", "충분히", "가능한 한", "일반적으로", "빠르게", "사용자 친화적으로" 등 정량화되지 않은 모호한 표현을 금지한다. 반드시 수치·조건·기준으로 대체한다.
- 약어/용어는 최초 등장 시 정의하고, 이후 동일 개념에는 동일 용어만 사용한다(용어집 관리).
- 수동태 대신 주체(시스템/행위자)를 명시한다.

## 5. 기능요구사항과 UML/SysML

기능요구사항 그룹마다 관련 동작을 시각화하는 다이어그램을 함께 제시한다.

- **표기 도구**: Markdown/아티팩트에 바로 렌더링되는 Mermaid를 기본으로 사용한다(Use Case 근사, Sequence, State Machine, Activity). SysML 고유 다이어그램(Requirement Diagram, Block Definition Diagram, Internal Block Diagram)이 필요하면 PlantUML의 SysML 매크로를 사용한다.
- **다이어그램 선택 기준**:
  - 액터와 시스템 기능의 관계 → Use Case Diagram
  - 상호작용/메시지 흐름 → Sequence Diagram
  - 상태 전이가 있는 동작 → State Machine Diagram
  - 여러 단계의 처리 흐름 → Activity Diagram
  - 요구사항 간 파생/만족/검증 관계 → SysML Requirement Diagram
  - 시스템 구성요소 구조 → SysML Block Definition Diagram
- 모든 다이어그램에는 관련 요구사항 ID를 캡션 또는 주석으로 명시하여 추적성을 유지한다.
- 다이어그램은 요구사항 서술을 대체하지 않는다. 서술이 1차 산출물이고 다이어그램은 이해를 돕는 보조 산출물이다.

## 6. 비기능요구사항과 ISO/IEC 25010

각 비기능요구사항은 다음을 반드시 포함한다.

1. **품질특성 매핑**: 성능효율성/호환성/사용성/신뢰성/보안성/유지보수성/이식성/기능적합성 중 해당 (부)특성.
2. **정량적 기준**: 측정 가능한 수치와 조건(예: "95퍼센타일 응답시간 200ms 이내, 동시 사용자 100명 조건").
3. **검증방법**: Test(시험) / Analysis(분석) / Inspection(검사) / Demonstration(시연) 중 하나 이상을 명시하고, 실제로 수행 가능한 절차·도구·환경까지 구체적으로 제시한다.

**검증방안의 실행 가능성 판단 기준** — 다음 중 하나라도 해당하면 그 검증방안은 사용하지 않고 재작성한다.
- 측정 도구/방법이 특정되지 않아 누가 수행해도 다른 결과가 나올 수 있는 경우
- 현재 프로젝트의 기술/자원/환경으로 접근 불가능한 도구나 데이터를 전제하는 경우
- 판정 기준(합격/불합격 임계값)이 없는 경우
- 무한하거나 비현실적인 시나리오 전수 검사를 요구하는 경우(대신 대표 시나리오/경계값/샘플링 등 실행 가능한 방법으로 대체)

## 7. ISO 26262 처리

- 안전 관련 요구사항인지 먼저 판단한다(상위 HARA/안전목표와 연결되는가).
- 안전 관련이면 ASIL(A~D)을 명시하고, 그 ASIL이 상위 안전목표로부터 어떻게 유도/상속(또는 분해)되었는지 근거를 남긴다. 근거가 없으면 "ASIL 근거 확인 필요"로 표시하고 임의로 등급을 매기지 않는다.
- 안전 요구사항은 Safety Goal → 기능안전요구사항(FSR) → 기술안전요구사항(TSR) → (시스템/SW) 안전요구사항의 추적 사슬 중 어디에 해당하는지 표시한다.
- 검증 엄격도(리뷰 방법, 독립성 수준)는 ASIL이 높을수록 엄격해야 하며, 이 스킬은 최소한 해당 요구사항에 "이 ASIL 수준에 맞는 검증/리뷰가 필요함"을 명시적으로 남긴다(구체적 리뷰 독립성 배정은 프로젝트 안전 계획의 몫이며 이 스킬 범위 밖임을 명확히 한다).
- 안전 무관 요구사항은 ASIL: QM으로 명시한다.

## 8. 추적성 확보 방안

- **ID 체계 우선순위**: 고객/상위 산출물이 이미 요구사항 ID 체계를 예고하거나 부여했다면(예: 고객 요구사양서의 추적성표가 특정 ID를 미리 지정) 그것을 그대로 사용하고, 아래 기본 체계로 임의로 바꾸지 않는다. 프로젝트별 채택 ID는 CLAUDE.md에 기록한다.
- **기본 ID 체계** (고객 지정 ID가 없을 때):
  - `REQ-STK-nnn` 이해관계자 요구사항
  - `REQ-SYS-Fnnn` / `REQ-SYS-Nnnn` 시스템 기능/비기능 요구사항
  - `REQ-SW-Fnnn` / `REQ-SW-Nnnn` 소프트웨어 기능/비기능 요구사항
  - `REQ-SAF-nnn` 안전 요구사항(ASIL 병기)
  - nnn은 3자리 이상 순번, 영구 결번 방지(삭제 시 ID 재사용 금지, "Deprecated"로 표시)
- **양방향 링크**: 모든 요구사항 항목에 `Trace-From`(상위 출처)과 `Trace-To`(하위 산출물: 설계/코드/테스트, 아직 없으면 "미정")를 필수로 기재한다.
- **추적성 매트릭스**: `docs/traceability/traceability-matrix.md`에 표 형태로 유지한다(이해관계자요구 ↔ 시스템요구 ↔ SW요구 ↔ 설계 ↔ 테스트케이스). 이 스킬을 사용해 요구사항을 신규 작성/변경할 때마다 이 매트릭스를 함께 갱신한다.
- 하위 산출물(설계/코드/테스트)이 아직 없다면 매트릭스에 "미정"으로 남기고, 이후 해당 산출물 작성 시 갱신해야 함을 결과 보고에 명시한다.

## 9. 일관성 확보 방안

작성/변경한 요구사항 전체에 대해 다음을 실제로 점검하고 결과를 보고한다.

- **ID 중복**: 동일 ID가 두 번 이상 사용되지 않았는가.
- **용어 일관성**: 동일 개념에 서로 다른 용어를 쓰지 않았는가(용어집 대조).
- **수치/조건 충돌**: 동일 대상에 대해 서로 다른 수치·조건을 요구하는 요구사항 쌍이 없는가.
- **논리적 모순**: 특정 조건에서 상반되는 동작을 동시에 요구하지 않는가.
- **범위 중복/공백**: 동일 기능을 중복 정의하거나, 필요한 기능이 요구사항 집합에서 빠져있지 않은가(가능한 범위에서 확인).

발견된 불일치는 반드시 목록으로 보고하고, 추측으로 임의 수정하지 않는다(작성자 확인이 필요한 항목은 "확인 필요"로 표시).
