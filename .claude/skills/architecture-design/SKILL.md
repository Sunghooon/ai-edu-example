# 아키텍처 설계 스킬

이 스킬은 A-SPICE 4.1 SYS.3(시스템 아키텍처 설계)/SWE.2(소프트웨어 아키텍처 설계)와 ISO 26262 Part 6(소프트웨어 수준 제품 개발)의 아키텍처 설계 원칙, SOLID 원칙을 준수하는 아키텍처 설계 산출물을 작성하기 위한 절차와 규칙을 정의한다.

## 0. 템플릿 우선순위 (필수 선행 절차)

1. 사용자가 이번 대화에서 직접 제시한 아키텍처 설계서 양식이 있으면 그것을 그대로 따른다.
2. 저장소 내 `docs/templates/architecture-template.md` 또는 사용자가 지정한 경로에 템플릿이 있으면 Glob/Grep으로 찾아 그것을 따른다.
3. 위 두 가지가 모두 없으면 "4. 기본 아키텍처 설계서 템플릿(Default)"을 사용하되, 산출물 상단에 "프로젝트 지정 템플릿이 없어 기본 템플릿을 사용함"이라고 명시한다.

## 1. 준수 표준 요약

- **A-SPICE 4.1 SYS.3/SWE.2 Base Practice 요지**: 아키텍처 개발, 요구사항의 아키텍처 요소 할당, 내/외부 인터페이스 정의, 동적 동작 기술, 자원 사용 목표 정의, **대안 아키텍처 평가(정의된 기준에 따른 비교)**, 양방향 추적성 확보, 일관성 확보, 합의된 아키텍처의 의사소통.
- **ISO 26262 Part 6 아키텍처 설계 원칙(대표 예시)**: 계층적/모듈적 구조, 컴포넌트·인터페이스 크기와 복잡도 제한, **높은 응집력**, **낮은 결합도**, 인터페이스에 대한 명확한 표기(데이터/프로토콜/사전조건/사후조건), 서로 다른 ASIL을 갖는 요소 간 공존 시 **간섭으로부터의 자유(freedom from interference)** 확보 또는 상위 ASIL로의 통일. (주: 정확한 조항 번호는 적용 중인 판(edition)에 따라 다를 수 있으므로, 실제 인증/심사 목적이라면 프로젝트가 채택한 ISO 26262 판본의 원문 조항을 대조해야 한다. 이 스킬은 원칙의 실무 적용에 초점을 둔다.)
- **SOLID 원칙**: 단일 책임(SRP), 개방-폐쇄(OCP), 리스코프 치환(LSP), 인터페이스 분리(ISP), 의존성 역전(DIP).

## 2. 아키텍처 설계 절차

1. **입력 확인**: 대상 시스템/소프트웨어 요구사항을 확인한다. `requirements-analysis` 스킬로 작성된 `docs/requirements/`와 `docs/traceability/traceability-matrix.md`가 있으면 그것을 입력으로 사용한다. 없으면 사용자에게 요구사항을 요청한다.
2. **후보 아키텍처 제안 (필수, 사용자 선정 전 진행 금지)**: "3. 후보 아키텍처 제안 형식"에 따라 최소 2개 이상의 후보 아키텍처 구조를 비교 제시하고, 사용자가 하나를 선택할 때까지 상세 설계로 진행하지 않는다.
3. **상세 설계 전개**: 사용자가 선택한 후보를 기준으로 컴포넌트 계층 구조, 책임(SRP 관점), 인터페이스, 동적 동작을 전개한다.
4. **인터페이스 정의**: "5. 인터페이스 정의 규칙"에 따라 컴포넌트 간 모든 통신을 인터페이스로만 정의한다. 컴포넌트 내부 상태에 대한 직접 접근은 금지한다.
5. **요구사항 할당**: 각 아키텍처 요소(컴포넌트/인터페이스)에 대응하는 요구사항 ID를 명시하여 `requirements-analysis` 스킬의 ID 체계와 연결한다.
6. **ASIL/간섭 분석**: "6. ISO 26262 ASIL 및 간섭 분석" 규칙에 따라 서로 다른 ASIL을 갖는 컴포넌트가 상호작용하는지 확인하고, 필요한 격리/분리 조치를 명시하거나 "확인 필요"로 남긴다.
7. **설계 원칙 검토**: "7. 설계 원칙 체크리스트"(응집도/결합도, SOLID, 인터페이스 전용 통신, 변경 유연성)를 실제로 점검하고 결과를 보고한다.
8. **통합 순서 정의**: "8. 컴포넌트 통합 순서 정의 규칙"에 따라 의존성 기반 통합 순서를 명시적으로 산출한다.
9. **추적성/일관성 갱신**: 추적성 매트릭스에 아키텍처 요소를 추가하고, 요구사항-아키텍처 간 미할당/모순 여부를 점검한다.
10. **결과 보고**: 사용한 템플릿, 선정된 후보와 선정 근거, 생성/수정 파일 목록, 통합 순서, 설계 원칙 검토 결과, 확인이 필요한 항목을 요약한다.

## 3. 후보 아키텍처 제안 형식

상세 설계 전에 다음 표 형식으로 최소 2개 이상의 후보를 제시하고 사용자의 선택을 기다린다.

| 후보 | 적용 패턴(예: 계층형/이벤트기반/컴포넌트기반/파이프-필터/마이크로커널) | 구조 개요 | 응집도/결합도 평가 | ASIL 분리 용이성 | 변경 유연성(OCP 관점) | 장점 | 단점 | 권장 상황 |
|---|---|---|---|---|---|---|---|---|
| 후보 A | | | | | | | | |
| 후보 B | | | | | | | | |

각 후보에는 고유 ID(`ARC-CAND-A`, `ARC-CAND-B`, ...)를 부여하고, 사용자가 선택한 후보 ID를 이후 산출물 전체에서 참조한다.

## 4. 기본 아키텍처 설계서 템플릿 (Default)

## 5. 인터페이스 정의 규칙

- 모든 컴포넌트 간 통신은 반드시 정의된 인터페이스를 통해서만 이루어진다. 컴포넌트 내부 데이터/상태에 대한 직접 접근(전역 변수 공유, 내부 구조체 직접 참조 등)은 금지한다.
- 각 인터페이스는 다음을 포함한다: 고유 ID(`ARC-IF-nnn`), 제공자/요구자 컴포넌트, 방향(단방향/양방향), 데이터 계약(타입/스키마), 통신 메커니즘(함수 호출/이벤트/메시지 등), 사전조건·사후조건, 오류 처리 계약, 버전.
- 인터페이스는 가능한 한 좁고 응집된 책임을 갖도록 정의한다(인터페이스 분리 원칙, ISP). 하나의 인터페이스에 서로 무관한 기능을 묶지 않는다.
- 상위 수준 모듈이 하위 수준 구현이 아니라 추상(인터페이스)에 의존하도록 설계한다(의존성 역전 원칙, DIP).

## 6. ISO 26262 ASIL 및 간섭 분석

- 각 컴포넌트에 요구사항으로부터 상속된 ASIL(또는 QM)을 표시한다.
- 서로 다른 ASIL을 갖는 컴포넌트가 인터페이스로 상호작용하는 경우, 다음 중 하나를 명시한다: (a) 더 높은 ASIL로 통일, (b) ASIL 분해(decomposition) 근거 제시, (c) 공간적/시간적 분리 등 간섭으로부터의 자유(freedom from interference) 조치.
- 근거가 확인되지 않으면 임의로 결정하지 않고 "ASIL/간섭 분석 확인 필요"로 남긴다.

## 7. 설계 원칙 체크리스트

- **높은 응집력**: 각 컴포넌트가 단일하고 명확한 책임을 갖는가(SRP).
- **낮은 결합도**: 컴포넌트 간 의존이 인터페이스(추상)를 통해서만 이루어지고, 구현 세부사항에 대한 의존이 없는가.
- **개방-폐쇄(OCP)**: 새 기능 추가 시 기존 컴포넌트 수정 없이 확장(신규 구현체 추가 등)으로 대응 가능한가.
- **리스코프 치환(LSP)**: 동일 인터페이스의 구현체를 교체해도 호출자의 기대 동작이 깨지지 않는가.
- **인터페이스 분리(ISP)**: 클라이언트가 사용하지 않는 인터페이스에 의존하도록 강요받지 않는가.
- **의존성 역전(DIP)**: 상위 정책이 하위 구현이 아니라 추상에 의존하는가.
- **변경 유연성**: 예상되는 변경 시나리오(요구사항 변경, 기술 교체 등)에 대해 영향 범위가 국소화되는가.

위 항목 중 미충족 항목은 재설계하거나, 불가피한 사유와 함께 "예외"로 명시한다.

## 8. 컴포넌트 통합 순서 정의 규칙

- 컴포넌트 간 의존성 그래프(누가 누구를 필요로 하는가)를 근거로 통합 순서를 정의한다.
- 순서 산정 전략은 명시적으로 선택하고 근거를 남긴다: 상향식(하위/공통 컴포넌트 우선), 하향식(제어 흐름 우선), 위험 기반(불확실성·위험이 큰 컴포넌트 우선) 중 프로젝트 상황에 맞는 전략을 선택한다.
- 각 통합 단계에 대해 순번, 대상 컴포넌트, 선행 조건(어떤 컴포넌트가 먼저 통합되어야 하는지), 통합 시 확인할 인터페이스를 명시한다.
- 이 통합 순서는 이후 SWE.5(소프트웨어 통합 및 통합시험) 산출물의 입력으로 사용됨을 산출물에 명시한다.

## 9. 추적성/일관성

- 아키텍처 요소 ID 체계: `ARC-COMP-nnn`(컴포넌트), `ARC-IF-nnn`(인터페이스).
- `docs/traceability/traceability-matrix.md`에 요구사항 ID(`REQ-*`) ↔ 아키텍처 요소 ID(`ARC-*`) 열을 추가/갱신한다.
- 다음을 점검하고 결과를 보고한다: 모든 요구사항이 하나 이상의 아키텍처 요소에 할당되었는가, 아키텍처 요소가 근거 요구사항 없이 존재하지 않는가, 인터페이스 정의가 서로 모순되지 않는가.

## 10. 산출물 배치 규칙

- 아키텍처 설계서: `docs/architecture/`
- 다이어그램: `docs/architecture/diagrams/`
- 추적성 매트릭스: `docs/traceability/traceability-matrix.md` (기존 파일에 이어서 갱신)

저장소에 기존 문서 구조가 있으면 그것을 우선한다.
