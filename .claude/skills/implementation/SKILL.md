# 구현 스킬

이 스킬은 이 저장소 `CLAUDE.md`의 "구현 지침"을 실행 절차로 구체화한 것이다. 구현은 `detailed-design` 스킬 산출물(상세설계 유닛과 유닛 검증기준)을 입력으로 받아 실제 코드와 테스트로 옮기는 단계이며, 작성 방식은 `tdd` 스킬(Red-Green-Refactor)을 따른다. 이 스킬은 "무엇을 만족해야 하는가"(품질 기준, 산출물)를 다루고, "어떤 순서로 작업하는가"는 `tdd` 스킬을 따른다.

## 0. 템플릿 우선순위 (필수 선행 절차)

1. 사용자가 이번 대화에서 직접 제시한 산출물 양식이 있으면 그것을 그대로 따른다.
2. 저장소의 표준 산출물 템플릿(`WP_Templates/`)을 사용한다. 세부 위치·형식별 처리 방법·라이선스 주의사항은 `references/templates.md`를 반드시 먼저 읽고 따른다.
3. 위 템플릿 파일을 저장소에서 찾을 수 없는 경우에만 최소 서식(측정 결과와 커버리지를 표로 정리한 Markdown 보고서)을 사용하고, 산출물 상단에 "표준 템플릿을 찾지 못해 최소 서식을 사용함"이라고 명시한다.

## 1. 준수 기준 요약 (CLAUDE.md 구현 지침)

- **언어/도구**: Python 3.14, 테스트는 `unittest` 사용.
- **개발 방식**: TDD(`tdd` 스킬을 반드시 사용). 실패하는 테스트 없이 구현 코드를 먼저 작성하지 않는다.
- **품질 지표 (반드시 준수)**:
  - 함수 순수코드라인 50라인 이하 (주석·공백·빈 줄 제외)
  - 함수 순환복잡도 10 이하
  - 중복 코드는 7라인까지 허용 (8라인 이상 중복은 리팩터링 대상)
  - 주석은 Doxygen 방식으로 작성하며, 전체 코드 대비 20% 이상
  - 함수명·변수명은 3글자 이상, 카멜케이스(camelCase) 사용
- **측정 방법**: 순환복잡도, 함수 라인수 등은 반드시 오픈소스 도구로 실제 측정한다(추정치를 보고하지 않는다). 프로젝트에 아직 도구가 설정되어 있지 않으면 사용자에게 어떤 도구를 채택할지 확인한다(예: 순환복잡도/라인수 측정에 `radon`, 스타일 검사에 `flake8`/`pylint`, 커버리지 측정에 `coverage.py` 등 오픈소스 도구).

## 2. 구현 절차

1. **입력 확인**: 구현 대상 상세설계 유닛(`DES-UNIT-*`)과 유닛 검증기준을 확인한다(`docs/detailed-design/` 또는 `detailed-design` 스킬 산출물). 없으면 먼저 상세설계가 필요함을 사용자에게 알리고 임의로 설계를 새로 만들지 않는다.
2. **TDD 사이클 수행**: `tdd` 스킬을 호출해 대상 유닛의 검증기준을 하나씩 Red-Green-Refactor로 구현한다.
3. **리팩터링 단계에서 품질 지표 적용**: 각 리팩터링 시점에 "3. 코드 품질 지표 체크리스트"를 적용한다.
4. **실측정**: 오픈소스 도구로 순환복잡도·함수 라인수·중복코드·주석비율을 실제로 실행해 측정하고 결과를 기록한다. 도구가 없으면 설치/설정 여부를 사용자에게 확인한다.
5. **커버리지 확인**: 상세설계 산출물의 유닛 검증기준이 테스트로 모두 커버되었는지 확인한다. 누락된 항목은 목록으로 보고한다.
6. **의존성/라이선스 갱신**: 새 외부 의존성을 추가했으면 `TPL-SBOM-001`(Python 의존성 SBOM/FOSS 라이선스 목록)을 갱신한다.
7. **산출물 작성**: 단위시험 명세서(`TPL-SWE4-001`)와 단위시험 결과서(`TPL-SWE4-002`)를 템플릿에 맞춰 생성/갱신한다.
8. **추적성 갱신**: 추적성 매트릭스에 소스 파일/테스트 파일 경로를 추가해 요구사항 ↔ 아키텍처 ↔ 상세설계 ↔ 코드/테스트까지 사슬을 완성한다.
9. **결과 보고**: 측정 지표 결과(라인수/복잡도/중복/주석비율)와 기준 대비 충족 여부, 미달 항목과 조치(리팩터링 또는 예외 사유), TDD 사이클 요약, 생성/수정 파일 목록, 추적성 갱신 내역을 보고한다.

## 3. 코드 품질 지표 체크리스트

각 함수/메서드에 대해 다음을 실제로 측정하고 점검한다. 임의로 "괜찮다"고 넘어가지 않는다.

| 지표 | 기준 | 측정 방법(예) |
|---|---|---|
| 함수 순수코드라인 | 50라인 이하 | 라인수 측정 도구(예: radon raw) |
| 함수 순환복잡도 | 10 이하 | 복잡도 측정 도구(예: radon cc) |
| 중복 코드 | 최대 7라인까지 허용, 8라인 이상은 리팩터링 | 중복탐지 도구 또는 수동 대조 |
| 주석 비율 | 전체 코드 대비 20% 이상, Doxygen 방식 | 라인수 측정 도구의 주석/코드 라인 비율 |
| 함수명/변수명 | 3글자 이상, camelCase | 정적 분석/스타일 검사 도구 또는 수동 점검 |

기준을 만족하지 못하면 리팩터링(`tdd` 스킬의 REFACTOR 단계)으로 해결한다. 불가피하게 기준을 벗어나야 하는 경우 그 사유를 명시적으로 "예외"로 보고하고 임의로 기준을 낮추지 않는다.

## 4. Doxygen 주석 규칙

- Python에서는 독스트링(`"""..."""`)에 Doxygen 스타일 태그(`@brief`, `@param`, `@return`, `@throws` 등)를 사용한다.
- 모든 공개 함수/클래스에 최소한 `@brief`, 파라미터가 있으면 `@param`, 반환값이 있으면 `@return`을 기술한다.
- 주석은 코드가 "무엇을 하는지"의 반복 설명이 아니라 "왜 이렇게 했는지"(비자명한 제약, 설계 근거)를 우선 포함하되, Doxygen 태그 항목(`@param`/`@return` 등)은 형식상 필요하므로 생략하지 않는다.

## 5. 네이밍 규칙

- 함수명·변수명은 3글자 이상이어야 한다(`i`, `x` 같은 단일/2글자 이름 금지, 관례적으로 널리 쓰이는 루프 인덱스도 이 프로젝트에서는 지양).
- camelCase를 사용한다(예: `calculateTotalPrice`, `userInputBuffer`). 이는 PEP 8의 snake_case 관례보다 이 프로젝트의 CLAUDE.md 지침을 우선한다.
- 클래스명 등 언어 자체의 관례(예: PascalCase 클래스명)와 충돌하는 부분이 있으면 사용자에게 확인한다.
