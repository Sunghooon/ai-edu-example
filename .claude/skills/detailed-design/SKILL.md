# 상세설계 스킬

이 스킬은 A-SPICE 4.1 SWE.3(소프트웨어 상세설계 및 유닛 구현)와 ISO 26262 Part 6의 유닛 설계 원칙, SOLID 원칙을 준수하는 상세설계 산출물을 작성하기 위한 절차와 규칙을 정의한다. 상세설계는 상위 아키텍처(`architecture-design` 스킬 산출물)를 유닛 수준으로 구체화하는 단계이며, 상위 아키텍처가 정의한 컴포넌트 경계와 인터페이스를 위반하지 않는 것을 전제로 한다.

## 적용 범위 (다른 스킬과의 경계)

- 이 스킬은 유닛 분해와 유닛 인터페이스, 유닛 검증기준(무엇을 검증해야 하는가)까지만 정의한다. 실제 코드와 테스트 코드는 작성하지 않는다 — `implementation`(품질 기준)과 `tdd`(작업 순서, Red-Green-Refactor)를 사용한다.
- 컴포넌트 경계와 상위 인터페이스는 `architecture-design`이 이미 정한 것을 그대로 따르며, 이 스킬에서 임의로 재정의하지 않는다.

## 0. 템플릿 우선순위 (필수 선행 절차)

1. 사용자가 이번 대화에서 직접 제시한 상세설계서 양식이 있으면 그것을 그대로 따른다.
2. 저장소의 표준 산출물 템플릿(`WP_Templates/`)을 사용한다. 세부 위치·형식별 처리 방법·라이선스 주의사항은 `references/templates.md`를 반드시 먼저 읽고 따른다. 핵심 템플릿:
   - SW 상세설계서: `WP_Templates/Engineering/SoftwareDetailedDesignAndUnitConstruction/TPL-SWE3-001_SW 상세설계서 템플릿.docx`
   - 상세설계 UML 및 호출관계: `WP_Templates/Engineering/SoftwareDetailedDesignAndUnitConstruction/TPL-SWE3-002_상세설계 UML 및 호출관계 템플릿.drawio`
   - Python 의존성 SBOM/FOSS 라이선스 목록(외부 의존성 도입 시): `WP_Templates/Engineering/SoftwareDetailedDesignAndUnitConstruction/TPL-SBOM-001_Python 의존성 SBOM FOSS 라이선스 목록 템플릿.xlsx`
   - 양방향 추적 매트릭스(요구사항-아키텍처-상세설계 연계): `WP_Templates/Engineering/Traceability/TPL-TRC-001_양방향 요구사항 추적 매트릭스 템플릿.xlsx`
   - 전체 템플릿 목록과 적용 산출물 매핑은 `WP_Templates/PRC-TPL-001_표준 산출물 양식 등록부.xlsx`를 따른다.
3. 위 템플릿 파일을 저장소에서 찾을 수 없는 경우에만 "4. 기본 상세설계서 템플릿(Default)"을 사용하되, 산출물 상단에 "표준 템플릿을 찾지 못해 기본 템플릿을 사용함"이라고 명시한다.

## 1. 준수 표준 요약

- **A-SPICE 4.1 SWE.3 Base Practice 요지**: 상세설계 개발(유닛 수준), 유닛 인터페이스 정의, 동적 동작 기술, 설계 기준에 따른 상세설계 평가, 유닛 검증기준 정의, 상위 아키텍처/요구사항과의 양방향 추적성 확보, 일관성 확보, 합의된 상세설계의 의사소통.
- **ISO 26262 Part 6 유닛 설계·코딩 원칙(대표 예시)**: 포인터 사용 제한, 초기화 이후 동적 메모리 할당 제한, 재귀 사용 제한, 인터럽트 사용에 대한 명확한 규칙, 함수당 단일 진입/단일 종료, 순환복잡도 제한, 무조건 분기(goto) 지양, 변수 사용 전 초기화, 전역변수·부작용 최소화. (주: 정확한 조항 번호와 세부 기준은 적용 판본과 프로젝트 코딩표준(MISRA C/C++ 등)에 따라 달라지므로, 실제 인증/심사 목적이라면 프로젝트가 채택한 표준 원문과 코딩 가이드라인을 대조해야 한다.)
- **SOLID 원칙**: 상위 아키텍처에서 정한 인터페이스와 책임 분리를 유닛 수준에서도 계승한다(SRP/OCP/LSP/ISP/DIP).

## 2. 상세설계 절차

1. **입력 확인**: 상위 아키텍처 산출물(컴포넌트, 인터페이스 정의, `docs/architecture/` 또는 `architecture-design` 스킬 산출물)과 관련 요구사항을 확인한다. 아키텍처 산출물이 없으면 먼저 아키텍처 설계가 필요함을 사용자에게 알린다.
2. **아키텍처 정합성 확인**: 대상 컴포넌트의 기존 인터페이스 정의를 확인한다. 상세설계 과정에서 상위 인터페이스를 변경해야 할 필요가 발견되면 임의로 변경하지 않고, 아키텍처 갱신이 필요함을 사용자에게 보고한다.
3. **유닛 분해**: 컴포넌트를 유닛(클래스/모듈/함수 등)으로 분해하고 단일 책임(SRP)을 갖도록 배정한다.
4. **유닛 인터페이스 정의**: 유닛 간 통신은 반드시 정의된 인터페이스로만 이루어지도록 하고, 상위 아키텍처 인터페이스와 모순되지 않게 한다.
5. **내부 설계 작성**: 각 유닛의 자료구조, 알고리즘, 호출관계(call graph)를 기술한다.
6. **동적 동작 기술**: 필요한 경우 유닛 수준 시퀀스/상태/활동 다이어그램(UML)을 작성한다.
7. **설계 원칙 검토**: "5. 설계 원칙 체크리스트"(ISO 26262-6 유닛 설계 원칙, SOLID)를 실제로 점검하고 결과를 보고한다.
8. **유닛 검증기준 정의**: "6. 유닛 검증기준 실행 가능성 기준"에 따라 SWE.4(유닛 검증)에서 바로 사용할 수 있는, 실행 가능한 검증기준(입력/기대출력/경계값/커버리지 목표)을 정의한다.
9. **의존성/라이선스 확인**: 외부 라이브러리나 오픈소스 의존성을 새로 도입하면 TPL-SBOM-001에 맞춰 의존성과 라이선스를 기록하고 호환성 문제가 없는지 확인한다.
10. **추적성 갱신**: 추적성 매트릭스에 상세설계 유닛을 추가해 요구사항 ↔ 아키텍처 요소 ↔ 상세설계 유닛의 사슬을 완성한다.
11. **일관성 검사**: 상세설계가 상위 아키텍처/요구사항과 모순되지 않는지, 유닛 간 책임 중복이나 누락이 없는지 점검한다.
12. **결과 보고**: 사용한 템플릿, 생성/수정 파일 목록, 설계 원칙 검토 결과, 정의된 유닛 검증기준, 추적성 갱신 내역, 확인이 필요한 항목을 요약한다.

## 3. ID 체계

- `DES-UNIT-nnn`: 상세설계 유닛(클래스/모듈/함수 등)
- `DES-IF-nnn`: 유닛 간 인터페이스(상위 아키텍처 인터페이스 `ARC-IF-nnn`과 구분하되, 어떤 `ARC-IF`를 구체화한 것인지 반드시 명시)
- 각 유닛은 자신이 속한 아키텍처 컴포넌트 ID(`ARC-COMP-nnn`)와 관련 요구사항 ID(`REQ-*`)를 함께 기재한다.

## 5. 설계 원칙 체크리스트

**ISO 26262-6 유닛 설계 원칙(대표 예시, 프로젝트 코딩표준과 대조 필요)**
- 포인터 사용이 제한적이고 정당화되는가.
- 초기화 이후 동적 메모리 할당이 제한/금지되는가(해당 안전 등급 기준).
- 재귀 사용이 제한되거나 스택 사용량이 분석되는가.
- 인터럽트 사용에 명확한 우선순위/보호 규칙이 있는가.
- 함수/모듈이 단일 진입/단일 종료 구조를 갖는가.
- 순환복잡도가 프로젝트 기준 이내로 관리되는가.
- 무조건 분기(goto) 등 제어흐름을 어렵게 하는 구조를 피했는가.
- 모든 변수가 사용 전 초기화되는가.
- 전역변수 사용과 부작용(side effect)이 최소화되는가.

**SOLID (유닛 수준 계승)**
- 각 유닛이 단일 책임을 갖는가(SRP).
- 확장 시 기존 유닛 수정 없이 대응 가능한가(OCP).
- 동일 인터페이스의 구현체 교체가 호출자 기대를 깨지 않는가(LSP).
- 클라이언트가 불필요한 인터페이스에 의존하지 않는가(ISP).
- 상위 로직이 구체 구현이 아닌 추상(인터페이스)에 의존하는가(DIP).

미충족 항목은 재설계하거나, 불가피한 사유와 함께 "예외"로 명시한다.

## 6. 유닛 검증기준 실행 가능성 기준

다음 중 하나라도 해당하면 그 검증기준은 사용하지 않고 재작성한다.

- 판정 방법/도구가 특정되지 않아 수행자에 따라 결과가 달라질 수 있는 경우
- 현재 프로젝트의 기술/자원/환경으로 접근 불가능한 도구·데이터를 전제하는 경우
- 합격/불합격 판정 임계값이 없는 경우
- 비현실적인 전수 입력 검사를 요구하는 경우(대신 경계값·대표값·동등분할 등 실행 가능한 방법으로 대체)

## 7. 추적성/일관성

- 추적성 매트릭스(`docs/traceability/traceability-matrix.md`)에 `DES-UNIT-*`, `DES-IF-*` 열을 추가/갱신한다.
- 다음을 점검하고 보고한다: 모든 아키텍처 요소가 하나 이상의 상세설계 유닛으로 구체화되었는가, 상세설계 유닛이 근거 아키텍처 요소 없이 존재하지 않는가, 유닛 인터페이스가 상위 아키텍처 인터페이스와 모순되지 않는가.
