# TDD 스킬 (obra/superpowers 기반)

이 스킬은 [obra/superpowers](https://github.com/obra/superpowers)의 `test-driven-development` 스킬(MIT License, Copyright (c) 2025 Jesse Vincent)을 이 저장소의 Python/unittest 환경, 상세설계 추적성 체계, Doxygen 주석 규칙에 맞게 각색한 것이다. 이 스킬은 "어떤 순서로 작업하는가"만 다룬다. 코드 품질 기준(라인수/순환복잡도/중복/주석비율/네이밍)은 `implementation` 스킬을 따른다.

## 핵심 원칙

- 테스트를 먼저 작성한다. 실패하는 것을 직접 확인한다. 통과시키는 최소한의 코드를 작성한다.
- **핵심 원칙**: 테스트가 실패하는 것을 직접 보지 않았다면, 그 테스트가 올바른 것을 검증하는지 알 수 없다.
- **규칙의 형식을 어기는 것은 규칙의 정신을 어기는 것이다.** ("일단 구현하고 나중에 테스트를 맞춰 끼운다"는 형식만 TDD를 흉내 낸 것이지 TDD가 아니다.)

## 철칙 (The Iron Law)

```
실패하는 테스트 없이 프로덕션 코드를 작성하지 않는다.
```

테스트보다 코드를 먼저 작성했다면 그 코드를 삭제하고 다시 시작한다. "참고용"으로 남겨두거나, 테스트를 쓰면서 그 코드를 "다듬어" 재사용하거나, 쳐다보지 않는다. 삭제는 삭제다. 테스트로부터 새로 구현한다.

## 언제 사용하는가

- **항상**: 신규 기능, 버그 수정, 리팩터링, 동작 변경
- **예외(사용자 확인 필요)**: 일회성 프로토타입, 자동 생성 코드, 단순 설정 파일

"이번만 TDD를 건너뛰자"는 생각이 든다면 멈춘다. 그것은 합리화다.

## 입력

- 구현 대상 유닛(가능하면 `detailed-design` 스킬 산출물의 `DES-UNIT-*`)과 그 유닛 검증기준(입력/기대출력/경계조건) 목록.
- 입력이 없으면 사용자에게 요청하거나 저장소의 상세설계 산출물을 탐색한다.

## Red-Green-Refactor 절차

대상 유닛의 검증기준 목록 중 아직 다루지 않은 항목이 있는 한 다음을 반복한다: **RED → 확인 → GREEN → 확인 → REFACTOR → 확인 → 다음**.

### RED — 실패하는 테스트 작성

다룰 검증기준 하나를 골라, 그 동작 하나만 검증하는 최소한의 테스트를 작성한다.

이 저장소에서는 모든 테스트 메서드가 다음 네 가지를 반드시 포함해야 한다.

1. **Doxygen 형식의 테스트 목적 설명**: 테스트 메서드의 독스트링에 `@brief`(테스트 목적)를 반드시 쓰고, 필요 시 `@param`/`@return`으로 테스트 데이터·기대값의 의미를 설명한다.
2. **사용한 테스트 기법 명시**: 동등분할(equivalence partitioning), 경계값분석(boundary value analysis), 결정테이블, 상태전이, 오류추정(error guessing) 등 이 테스트 케이스를 도출한 기법을 `@technique` 태그로 명시한다.
3. **긍정/부정 케이스 여부 명시**: 정상 동작을 검증하는 긍정 케이스인지, 예외·오류·경계 위반을 검증하는 부정 케이스인지 `@case`(긍정/부정)로 명시한다.
4. **추적 ID**: 어떤 요구사항/유닛 검증기준을 다루는지 `@covers`로 ID를 명시한다.

예시(Python, `unittest`):

```python
import unittest

class RetryOperationTest(unittest.TestCase):
    def test_retries_failed_operation_three_times(self):
        """
        @brief 실패하는 작업을 3회까지 재시도한 뒤 마지막 시도의 결과를 반환하는지 검증한다.
        @technique 동등분할 (재시도 횟수가 임계값 미만인 그룹)
        @case 긍정 (정상적으로 재시도 후 성공하는 경우)
        @covers DES-UNIT-014 / REQ-SW-F021
        """
        attempts = {"count": 0}

        def flakyOperation():
            attempts["count"] += 1
            if attempts["count"] < 3:
                raise RuntimeError("fail")
            return "success"

        result = retryOperation(flakyOperation)

        self.assertEqual(result, "success")
        self.assertEqual(attempts["count"], 3)

    def test_raises_after_exceeding_max_retries(self):
        """
        @brief 재시도 한도를 초과해 계속 실패하면 마지막 예외가 그대로 전파되는지 검증한다.
        @technique 경계값분석 (재시도 횟수 = 임계값)
        @case 부정 (한도 초과로 실패가 계속되는 경우)
        @covers DES-UNIT-014 / REQ-SW-F021
        """
        def alwaysFails():
            raise RuntimeError("fail")

        with self.assertRaises(RuntimeError):
            retryOperation(alwaysFails)
```

좋은 테스트: 단일 동작만 검증하고, 이름과 독스트링만으로 의도가 분명하며, 실제 코드를 사용한다(불가피한 경우가 아니면 목(mock) 금지). 나쁜 예: `test_retry_works`처럼 모호한 이름, 실제 동작 대신 목의 호출 횟수만 검증.

### RED 확인 — 실패를 직접 확인 (필수, 절대 생략 금지)

```bash
python -m unittest path.to.test_module -v
```

다음을 확인한다.
- 테스트가 (에러가 아니라) **실패**하는가
- 실패 메시지가 예상한 내용인가
- 기능이 없어서 실패하는 것이지, 오타 때문이 아닌가

테스트가 통과해버리면 이미 존재하는 동작을 테스트하는 것이므로 테스트를 고친다. 테스트가 에러를 내면 에러를 고치고 "올바르게 실패"할 때까지 재실행한다.

### GREEN — 최소 구현

테스트를 통과시키는 가장 단순한 코드만 작성한다. 다른 검증기준을 미리 구현하거나(YAGNI 위반), 요청받지 않은 옵션·매개변수를 추가하지 않는다.

### GREEN 확인 — 통과를 직접 확인 (필수)

```bash
python -m unittest path.to.test_module -v
```

확인 사항: 대상 테스트 통과, 기존 테스트도 모두 통과, 출력에 에러·경고가 없음(pristine). 테스트가 실패하면 테스트가 아니라 코드를 고친다. 다른 테스트가 깨지면 그 자리에서 고친다.

### REFACTOR — 정리

Green 상태에서만 진행한다. 중복 제거, 이름 개선, 헬퍼 추출을 수행하고 새 동작을 추가하지 않는다. 이 저장소에서는 이 단계에서 `implementation` 스킬의 코드 품질 지표(함수 순수코드라인 ≤50, 순환복잡도 ≤10, 중복코드 최대 7라인, Doxygen 주석 20% 이상, 함수/변수명 3글자 이상 camelCase)를 적용한다. 리팩터링 후 테스트를 다시 실행해 여전히 Green인지 확인한다.

### 반복

다음 검증기준에 대해 RED부터 반복한다. 모든 유닛 검증기준을 커버할 때까지 계속한다.

## 좋은 테스트를 쓰는 법

테스트를 작성하거나 목(mock)을 추가할 때는 반드시 `references/writing-good-tests.md`를 먼저 읽고 따른다. 핵심 요지는 다음과 같다.

- 테스트를 쓰기 전에 "이 테스트를 실패하게 만드는 프로덕션 변경이 무엇인가"를 먼저 답한다. 답할 수 없으면 관찰 가능한 동작 중심으로 다시 설계한다.
- 기대값은 테스트 대상 코드(또는 그 헬퍼)로 계산하지 않고, 손으로 도출한 리터럴/픽스처를 사용한다.
- 목 자체의 호출 여부만 검증하지 않는다 — 실제 동작을 검증한다.
- 목을 쓰기 전에 실제 메서드의 부작용을 먼저 파악하고, 느리거나 외부적인 부분만 목으로 대체한다.
- 목 응답은 실제 구조를 완전히 반영한다(테스트가 읽는 필드만 채우지 않는다).
- 테스트에서만 필요한 정리(cleanup) 코드는 프로덕션 클래스가 아니라 테스트 유틸리티에 둔다.
- 완료 전 "돌연변이 검사(mutation check)": 프로덕션 코드를 한 곳씩 고의로 틀리게 바꿔봤을 때, 그 각각을 잡아내는 테스트가 최소 하나씩 있는지 확인한다.

## 흔한 합리화와 반박

| 변명 | 실제 |
|---|---|
| "너무 단순해서 테스트할 필요 없다" | 단순한 코드도 깨진다. 테스트는 30초면 된다. |
| "나중에 테스트하겠다" | 나중에 작성한 테스트는 바로 통과해버려 아무것도 증명하지 못한다. 실패를 본 적이 없으므로 버그를 잡을 수 있다는 증거가 없다. |
| "이미 수동으로 테스트했다" | 수동 테스트는 기록도, 재실행도 안 되고 압박 속에서 케이스를 놓치기 쉽다. |
| "지금까지 쓴 시간이 아깝다" | 매몰비용 오류다. 신뢰할 수 없는 코드를 유지하는 것이 진짜 낭비다. |
| "TDD는 느리다" | TDD가 실용적인 길이다 — 커밋 전에 버그를 잡고 회귀를 막는다. |
| "참고용으로 남겨두고 테스트부터 쓰겠다" | 결국 그 코드를 다듬어 재사용하게 된다. 그것도 사후 테스트다. |

## 위험 신호 — 즉시 중단하고 다시 시작

- 테스트보다 코드를 먼저 작성함
- 테스트가 바로 통과해버림
- 왜 실패했는지 설명할 수 없음
- 테스트를 "나중에" 추가함
- "이번만"이라고 합리화하는 중

이 중 하나라도 해당하면 코드를 삭제하고 TDD로 다시 시작한다. 사용자의 명시적 허락 없이는 예외가 없다.

## 완료 전 체크리스트

- [ ] 새 함수/메서드마다 테스트가 있는가
- [ ] 각 테스트가 구현 전에 실패하는 것을 직접 확인했는가
- [ ] 각 테스트가 예상한 이유로 실패했는가(기능 없음이지 오타가 아님)
- [ ] 각 테스트를 통과시키는 최소한의 코드를 작성했는가
- [ ] 모든 테스트가 통과하는가
- [ ] 출력이 깨끗한가(에러·경고 없음)
- [ ] 실제 코드를 사용했는가(불가피한 경우만 목 사용)
- [ ] 경계·오류 케이스를 다뤘는가
- [ ] 각 테스트에 Doxygen 목적 설명(`@brief`), 사용 기법(`@technique`), 긍정/부정 케이스(`@case`), 추적 ID(`@covers`)가 모두 있는가

체크박스를 모두 채울 수 없다면 TDD를 건너뛴 것이다 — 다시 시작한다.

## 막혔을 때

| 문제 | 해결 |
|---|---|
| 테스트를 어떻게 짤지 모르겠다 | 원하는 API를 먼저 적고, 단언(assert)부터 작성한다. 필요하면 사용자에게 확인한다. |
| 테스트가 너무 복잡하다 | 설계가 너무 복잡한 것이다. 인터페이스를 단순화한다. |
| 전부 목을 써야 한다 | 코드가 과하게 결합되어 있다. 의존성 주입을 사용한다. |
| 테스트 준비(setup)가 방대하다 | 헬퍼로 추출한다. 그래도 복잡하면 설계를 단순화한다. |

## 디버깅 연계 (회귀 테스트)

버그를 발견하면 그 버그를 재현하는 실패 테스트를 먼저 작성한 뒤(RED), 수정하고(GREEN), 정리한다(REFACTOR). 테스트 없이 버그를 고치지 않는다.

## 최종 규칙

```
프로덕션 코드 → 먼저 실패한 테스트가 존재해야 한다
그렇지 않다면 → TDD가 아니다
```
