# 좋은 테스트를 쓰는 법

**이 문서를 읽어야 할 때**: 테스트를 작성/수정하거나, 목(mock)을 추가하거나, 테스트용 정리(cleanup)/헬퍼 메서드를 추가할 때.

[obra/superpowers](https://github.com/obra/superpowers)의 `writing-good-tests.md`(MIT License, Copyright (c) 2025 Jesse Vincent)를 이 저장소의 Python/unittest 환경에 맞게 번역·각색했다.

## 개요

테스트는 특정한 결함을 잡기 위해 존재한다. 두 가지 원칙이 모든 것을 지배한다.

```
1. 모든 테스트는 자신이 잡아내는 결함을 이름 붙일 수 있어야 한다
2. 모든 테스트는 실제 대상을 실행해야 한다
```

엄격한 TDD는 이 두 가지를 자연스럽게 만족시킨다. 먼저 작성되어 실제 코드에 대해 실패하는 것을 확인한 테스트는 이미 "실패할 수 있음"을 증명했고, 실제 의존성이 느리거나 외부적임이 드러났을 때만 목(mock)을 쓸 자격을 얻는다.

## 원칙 1: 결함의 이름을 말할 수 있어야 한다

테스트 본문을 작성하기 전에 먼저 답한다: **어떤 프로덕션 코드 변경이 이 테스트를 실패하게 만드는가 — 그리고 그 변경은 버그인가, 의도적인 결정인가?** 테스트는 잘못된 분기, 누락된 부작용, 잘못된 인자, 경계 조건, 깨진 계약을 잡아낼 때 존재할 자격을 얻는다.

**기대값은 독립적으로 도출한다.** 리터럴 값과 직접 확인한 픽스처를 사용한다. 테이블 기반 테스트에서 `want` 값을 리터럴로 쓰는 방식을 선호한다. 테스트 대상 코드(또는 그 헬퍼)로 계산한 기대값은 그 코드가 무엇을 하든 항상 통과한다.

```python
# 잘못된 예: 동일한 빌더로 양쪽을 계산 — 항상 참
expected = buildSearchQuery({"tag": "urgent"})
assert buildSearchQuery({"tag": "urgent"}) == expected

# 올바른 예: 손으로 도출한 리터럴
assert buildSearchQuery({"tag": "urgent"}) == 'tag:"urgent"'
```

**변경 감지기(change detector)를 만들지 않는다.** 의도적인 결정만 실패하게 만드는 테스트(상수 값, 정확한 메시지 문구, 내부 구조 등)는 재설계 때마다 울리고 정작 버그에는 잠들어 있다. 결정 자체가 아니라 그 결정에 의존하는 동작을 테스트한다. `assert MAX_RETRIES == 5`가 아니라 "실패한 호출은 5번 재시도되고 6번째 시도는 일어나지 않는다"를 검증한다.

**텍스트가 아니라 동작을 검증한다.** 스크립트/문서가 정확히 어떤 줄을 포함하는지 확인하는 것은 소스가 소스임을 증명할 뿐이다. 통제된 입력으로 스크립트를 실행해 출력·부작용·종료코드를 검증한다.

**프레임워크가 아니라 자신의 코드를 검증한다.** 자신의 코드가 경계에서 만드는 계약(등록하는 라우트, 만들어내는 쿼리, 생성하는 페이로드)을 테스트한다. 업스트림(라이브러리/프레임워크)의 동작은 그 유지관리자의 테스트 몫이다.

### 게이트 함수

```
테스트 본문을 작성하기 전에:
  이 테스트를 실패하게 만드는 프로덕션 변경을 이름 붙인다.

  이름 붙일 수 없다면            → 관찰 가능한 동작 중심으로 재설계
  "소스 텍스트가 바뀌었다"        → 아티팩트를 실행해 그 효과를 검증
  의도적 결정만 실패시킨다면      → 변경 감지기다; 그 결정에 의존하는 동작을 테스트

  기대값이 테스트 대상 코드 없이 도출되었는지 확인한다.
  대상 코드/헬퍼의 로직을 재사용한다면:
    리터럴이나 직접 확인한 픽스처로 교체한다
```

## 원칙 2: 실제 대상을 실행한다

**목(mock)은 그 자체로는 아무 것도 증명하지 않는다.** 목에 대한 단언은 목이 존재하면 통과하고 없으면 실패할 뿐, 실제 컴포넌트에 대해서는 아무것도 말하지 않는다. 실제 컴포넌트의 동작을 검증하거나, 목을 제거하거나, 그 단언을 삭제한다.

```python
# 올바른 예: 실제 동작 검증
self.assertTrue(response.headers.get("X-Request-Id"))

# 잘못된 예: 목의 존재 여부만 검증
self.assertTrue(mock_client.called)
```

**적절한 수준에서 목을 사용한다.** 실제 메서드를 대체하기 전에 그 부작용을 모두 파악하고, 느리거나 외부적인 연산만 목으로 대체하며 테스트가 의존하는 나머지는 실제로 남겨둔다. 확신이 없으면 먼저 실제 구현으로 테스트를 실행해 무엇이 실제로 일어나는지 관찰한다.

**더블(double)을 구체적으로 만든다.** 인자, 호출 횟수, 순서가 계약의 일부라면 그것을 단언한다. 아무것이나 받아주는 가짜(fake)는 아무것도 검증하지 않는다. 각 분기(성공/오류/잘못된 입력)마다 별도의 픽스처나 스파이를 둔다.

**실제 데이터 구조를 완전히 반영한다.** 목 응답은 실제로 존재하는 구조 전체(문서화된 모든 필드)를 반영해야 한다. 테스트가 읽는 필드만 채운 부분적인 목은, 하위 코드가 누락된 필드를 읽을 때 조용히 실패한다 — 테스트는 통과하는데 통합은 깨진다.

**테스트 전용 정리(cleanup)는 프로덕션 클래스에 두지 않는다.** 테스트에서만 호출되는 메서드는 프로덕션 클래스의 `destroy()` 같은 메서드가 아니라 테스트 유틸리티에 둔다.

**목 설정이 테스트 로직보다 커지면 실제 컴포넌트를 쓰는 통합 테스트로 전환한다.**

### 게이트 함수

```
목이나 테스트 헬퍼를 추가하기 전에:
  실제 메서드의 부작용을 나열하고, 테스트가 의존하는 부작용은 실제로 남긴다.
  느리거나 외부적인 수준만 목으로 대체한다.

  목 응답이 실제 구조를 완전히 반영하는지 확인한다.

  테스트에서만 호출되는 메서드는 프로덕션이 아니라 테스트 유틸리티에 둔다.

  목 자체를 단언하려 하고 있다면?
    목을 제거하거나 그 단언을 삭제한다.
```

## 구현과 함께 완성되는 테스트

TDD 사이클(실패하는 테스트 → 최소 구현 → 리팩터링)이 "완료"의 정의다. 그 동작이 필요로 하는 테스트만 남긴다 — 사소한 코드와 사람이 읽을 산문에는 테스트가 필요 없고, 절차를 만족시키기 위해서만 쓴 테스트는 유지보수 비용만 영구히 남긴다.

## 돌연변이 검사(Mutation Check)

작업을 마치기 전에 프로덕션 코드를 마음속으로 한 곳씩 고의로 틀리게 바꿔본다. 현실적인 각 변형마다 최소 하나의 테스트가 실패해야 한다.

- 잘못된 상수·인자
- 잘못된 분기 처리
- 누락된 상태 변경·부작용
- 빈 값/기본값 반환
- 0, 빈 값, null, 권한 없음, 잘못된 형식의 입력에 대한 검증 누락

아무 테스트도 잡아내지 못하는 변형이 있다면, 그 동작은 보호되지 않은 것이거나 그 테스트가 동어반복(tautology)이라는 뜻이다.

## 빠른 참조

| 상황 | 할 일 |
|---|---|
| 아무 테스트나 작성할 때 | 그것이 잡아내는 결함(버그, 결정이 아님)을 이름 붙인다 |
| 기대값을 만들 때 | 손으로 도출한다 — 테스트 대상 코드로 계산하지 않는다 |
| 스크립트나 문서를 테스트할 때 | 실행하거나 그 소비자를 압박 테스트한다 — 텍스트를 grep하지 않는다 |
| 의존성 테스트를 쓰려 할 때 | 그들의 문서화된 동작이 아니라 자신의 경계 계약을 테스트한다 |
| 목이 된 요소를 단언하려 할 때 | 실제 컴포넌트를 테스트하거나 목을 제거한다 |
| 메서드를 목으로 만들려 할 때 | 부작용을 먼저 파악하고, 느리거나 외부적인 수준만 목으로 만든다 |
| 목 응답을 만들 때 | 실제 구조를 완전히 반영한다 |
| 테스트 전용 정리가 필요할 때 | 테스트 유틸리티에 둔다 |
| 목 설정이 비대해질 때 | 실제 컴포넌트를 쓰는 통합 테스트로 전환한다 |
| 테스트 파일을 마무리할 때 | 돌연변이 검사를 수행한다 |

## 경고 신호

- 준비(setup)와 단언이 같은 객체를 공유해 항상 같아지도록 되어 있다
- 패닉·크래시·셀렉터 누락으로만 테스트가 실패할 수 있다
- 의도적인 변경마다 항상 실패하고, 실수로 인한 결함에는 실패하지 않는다
- 기대값이 반복문·빌더·헬퍼 뒤에 숨어 있다
- 소스 텍스트를 grep하거나, 제거된 심볼이 계속 없는지만 확인한다
- 프레임워크만 남아 있어도 여전히 의미 있는 테스트다
- 커버리지를 위해 존재할 뿐 어떤 부작용·결과도 확인하지 않는다
- `*-mock` 테스트 ID를 단언하거나, 목을 제거하면 실패한다
- 특정 메서드가 테스트 파일에서만 호출된다
- 목 설정이 테스트의 절반을 넘거나, 왜 그 목이 필요한지 설명할 수 없다
- "혹시 몰라서" 목을 쓴다
