# 소프트웨어 통합시험 스킬

이 스킬은 A-SPICE 4.1 SWE.5(소프트웨어 통합 및 통합시험)와 ISO 26262 Part 6의 소프트웨어 통합시험 원칙을 준수하는 통합시험 산출물을 작성하기 위한 절차와 규칙을 정의한다. 이 스킬은 `architecture-design` 스킬 산출물(컴포넌트, 인터페이스, 통합 순서)과 `detailed-design`/`coding`/`tdd` 스킬로 이미 유닛 검증(SWE.4)을 마친 코드를 입력으로 받아, 컴포넌트를 정의된 순서대로 결합하며 인터페이스 수준의 동작을 검증한다.

## 0. 템플릿 우선순위 (필수 선행 절차)

1. 사용자가 이번 대화에서 직접 제시한 산출물 양식이 있으면 그것을 그대로 따른다.
2. 저장소의 표준 산출물 템플릿(`WP_Templates/`)을 사용한다. 세부 위치·형식별 처리 방법·라이선스 주의사항은 `references/templates.md`를 반드시 먼저 읽고 따른다. 핵심 템플릿:
   - SW 통합전략 및 통합시험 명세서: `WP_Templates/Engineering/SoftwareComponentVerificationAndIntegrationVerification/TPL-SWE5-001_SW 통합전략 및 통합시험 명세서 템플릿.docx`
   - SW 통합시험 케이스: `WP_Templates/Engineering/SoftwareComponentVerificationAndIntegrationVerification/TPL-SWE5-002_SW 통합시험 케이스 템플릿.xlsx`
   - SW 통합시험 결과서: `WP_Templates/Engineering/SoftwareComponentVerificationAndIntegrationVerification/TPL-SWE5-003_SW 통합시험 결과서 템플릿.xlsx`
   - 양방향 추적 매트릭스: `WP_Templates/Engineering/Traceability/TPL-TRC-001_양방향 요구사항 추적 매트릭스 템플릿.xlsx`
   - 전체 템플릿 목록과 적용 산출물 매핑은 `WP_Templates/PRC-TPL-001_표준 산출물 양식 등록부.xlsx`를 따른다.
3. 위 템플릿 파일을 저장소에서 찾을 수 없는 경우에만 "6. 기본 산출물 서식(Default)"을 사용하고, 산출물 상단에 "표준 템플릿을 찾지 못해 기본 서식을 사용함"이라고 명시한다.

## 1. 준수 표준 요약

- **A-SPICE 4.1 SWE.5 Base Practice 요지**: 통합전략 개발, 통합시험 검증기준 정의, 전략에 따른 통합시험 명세, 시험 수행 및 결과 평가, 시험 환경 적정성 확보, 요구사항/아키텍처와의 양방향 추적성, 일관성 확보.
- **ISO 26262 Part 6 소프트웨어 통합시험(대표 예시, 판본별 조항 대조 필요)**:
  - **시험 기법**: 요구사항 기반 테스트(requirements-based test), 인터페이스 테스트(interface test), 결함주입 테스트(fault injection test), 자원사용 테스트(resource usage test), 필요 시 모델-코드 백투백 비교 테스트.
  - **구조적 커버리지 지표(소프트웨어 통합 수준)**: **함수 커버리지(function coverage)**, **호출 커버리지(call coverage)**. 표준은 ASIL 등급에 따라 권고 수준을 달리하지만, **이 프로젝트는 등급과 무관하게 두 지표 모두 100% 달성을 목표로 한다**(표준의 최소 권고보다 엄격한 프로젝트 방침).

## 2. 테스트 베이시스 (필수 입력)

- **아키텍처 설계서**(`architecture-design` 스킬 산출물, `docs/architecture/`): 컴포넌트 목록, 인터페이스 정의(`ARC-IF-*`), **컴포넌트 통합 순서**(아키텍처 산출물 9절).
- 아키텍처 산출물이 없거나 통합 순서가 정의되어 있지 않으면 먼저 아키텍처 설계가 필요함을 사용자에게 알리고, 임의로 통합 순서를 새로 지어내지 않는다.
- 대상 컴포넌트들의 유닛 검증(SWE.4)이 완료되었는지 확인한다. 완료되지 않은 컴포넌트가 통합 대상에 포함되어 있으면 그 사실을 보고하고, 임의로 넘어가지 않는다.

## 3. 통합시험 절차

1. **입력 확인**: 아키텍처 설계서의 인터페이스와 통합 순서, 유닛 검증 완료 여부를 확인한다.
2. **통합전략 수립**: 아키텍처의 통합 순서를 그대로 반영해 통합 단계(increment)를 정의한다. 각 단계마다 이번에 새로 추가되는 컴포넌트와, 그로 인해 새로 검증해야 하는 인터페이스를 명시한다. 통합 순서를 임의로 재배열하지 않는다 — 순서를 바꿔야 할 필요가 발견되면 아키텍처 갱신이 필요함을 사용자에게 보고한다.
3. **단계별 테스트 설계**: 각 통합 단계에서 새로 활성화되는 인터페이스에 대해 "4. ISO 26262-6 시험 기법 적용"에 따라 테스트 케이스를 설계한다.
4. **단계적 실행**: 정의된 통합 순서대로 단계를 실행한다. 한 단계가 실패하면(테스트 실패, 커버리지 미달) 다음 단계로 진행하지 않고 원인을 먼저 해결한다.
5. **커버리지 측정**: "5. 커버리지 목표와 측정" 규칙에 따라 함수 커버리지와 Call 커버리지를 실제로 측정한다. 100% 미달 시 원인을 분석해 테스트를 보강하거나, 도달 불가능한 코드임을 근거와 함께 예외로 기록한다. 측정 없이 "충분하다"고 판단하지 않는다.
6. **산출물 작성**: TPL-SWE5-001(통합전략 및 통합시험 명세서), TPL-SWE5-002(통합시험 케이스), TPL-SWE5-003(통합시험 결과서)를 템플릿에 맞춰 생성/갱신한다.
7. **추적성 갱신**: 추적성 매트릭스에 통합시험 케이스(`ITC-*`)를 추가해 요구사항 ↔ 아키텍처 ↔ 상세설계 ↔ 코드 ↔ 통합시험까지 사슬을 완성한다.
8. **일관성 검사**: 아키텍처의 모든 인터페이스가 하나 이상의 인터페이스 테스트로 커버되었는지, 통합 순서의 모든 단계가 실제로 테스트되었는지, 커버리지 결과가 서로 모순되지 않는지 점검한다.
9. **결과 보고**: 사용한 템플릿, 통합 단계별 진행 결과, 커버리지 측정 결과(함수/Call)와 100% 대비 충족 여부, 미달 항목과 조치/예외 사유, 생성/수정 파일 목록, 추적성 갱신 내역을 요약한다.

## 4. ISO 26262-6 시험 기법 적용

각 통합 단계에서 새로 활성화되는 인터페이스마다 다음 기법을 적용한다(해당하지 않는 기법은 사유를 명시하고 생략 가능).

- **요구사항 기반 테스트**: 통합된 컴포넌트가 함께 구현하는 요구사항(`REQ-SW-F*`)에 대응하는 시나리오를 컴포넌트 경계를 넘나들며 검증한다.
- **인터페이스 테스트**: 아키텍처에서 정의된 인터페이스 계약(데이터 형식, 사전조건, 사후조건, 오류 처리)이 실제 컴포넌트 간 호출에서 지켜지는지 검증한다.
- **결함주입 테스트**: 인터페이스에 비정상 입력, 지연, 오류 응답 등을 주입했을 때 정의된 오류 처리·복구 동작이 실제로 일어나는지 검증한다.
- **자원사용 테스트**: 아키텍처에서 정의한 자원 사용 목표(타이밍, 메모리 등)가 통합된 상태에서도 충족되는지 검증한다(목표가 정의되어 있을 때만 수행).
- **백투백 비교 테스트**: 모델 기반 설계 산출물이 있고 모델-코드 일치 확인이 프로젝트 범위에 포함될 때만 수행한다. 해당하지 않으면 생략하고 그 사실을 명시한다.

각 테스트 케이스에는 어떤 기법을 사용했는지, 어떤 인터페이스(`ARC-IF-*`)/요구사항(`REQ-*`)을 다루는지 명시한다.

## 5. 커버리지 목표와 측정

- **목표**: 통합 대상 코드 전체에 대해 **함수 커버리지 100%**, **Call 커버리지 100%**를 달성한다.
- **측정 원칙**: 반드시 실행 가능한 오픈소스/표준 도구로 실제 측정한다. 추정치를 보고하지 않는다. 프로젝트에 함수/Call 커버리지를 측정할 도구가 설정되어 있지 않으면(일반적인 라인/브랜치 커버리지 도구만으로는 부족할 수 있음) 어떤 도구를 채택할지 사용자에게 확인한다.
- **100% 미달 시 처리**: 다음 중 하나로만 종결한다. 임의로 목표를 낮추지 않는다.
  1. 테스트 케이스를 보강해 실제로 100%를 달성한다.
  2. 코드가 구조적으로 도달 불가능함(방어적 코드, 죽은 코드 등)을 근거와 함께 확인하고, 근거와 해당 코드 위치를 명시한 예외로 기록한다.
- 함수 커버리지: 정의된 모든 함수가 최소 한 번 이상 호출되었는지.
- Call 커버리지: 코드 내 모든 함수 호출 지점(call site)이 최소 한 번 이상 실행되었는지.

## 6. 기본 산출물 서식 (Default)

프로젝트 템플릿이 없을 때 사용하는 최소 서식이다.

```
# 소프트웨어 통합시험 명세/결과서

## 1. 테스트 베이시스
- 아키텍처 설계서 링크, 인터페이스 목록, 통합 순서

## 2. 통합전략 및 단계 구성
| 단계 | 신규 통합 컴포넌트 | 신규 활성화 인터페이스 | 선행 조건 |
|---|---|---|---|

## 3. 통합시험 케이스
| 테스트 ID(ITC) | 대상 인터페이스(ARC-IF) | 관련 요구사항(REQ) | 적용 기법 | 시나리오 | 기대 결과 |
|---|---|---|---|---|---|

## 4. 실행 결과

|---|---|---|---|

| 지표 | 목표 | 실측값 | 미달 시 조치/예외 사유 |
|---|---|---|---|
| 함수 커버리지 | 100% | | |
| Call 커버리지 | 100% | | |

## 6. 추적성

```

## 7. ID 체계

- `ITC-nnn`: 통합시험 케이스(Integration Test Case)
- 각 케이스는 대상 인터페이스(`ARC-IF-*`), 관련 요구사항(`REQ-*`), 통합 단계 번호를 함께 기재한다.

## 8. 산출물 배치 규칙

- 통합시험 문서: `docs/integration-test/`
- 커버리지 리포트: `docs/integration-test/coverage/`
- 추적성 매트릭스: `docs/traceability/traceability-matrix.md` (기존 파일에 이어서 갱신)

저장소에 기존 문서 구조가 있으면 그것을 우선한다.
